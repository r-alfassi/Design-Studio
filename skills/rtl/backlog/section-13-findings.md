# Backlog: Three findings from Section 13 not yet written into the skill

**Status:** Not started — captured for a future documentation pass, not executed inline to avoid interrupting live section work.

## 1. Batch reorder scripts need idempotency safety — the Header COPY double-run bug

**What happened:** The `Header COPY` icon-swap fix was applied twice across overlapping scope (once early in the session, once again later as part of a broader batch). Because the swap operation (`insertChild(0, b); insertChild(2, a)`) has no memory of whether a given node was already processed, some of the 17 `Header COPY` instances ended up net-single-swapped (correct) while others ended up net-double-swapped (silently back to original, wrong) — purely depending on which runs happened to touch which nodes. This was only caught by screenshotting a specific instance and noticing the visible icon was on the wrong side; there was no error, no log signal, nothing structurally different about the "wrong" nodes that a property scan would catch.

**Why it's dangerous:** A swap (or any operation that's its own inverse) is exactly the kind of fix an operator is tempted to "just run again" if unsure whether it already ran — and doing so doesn't error, it silently undoes the work. The bug surfaces only through visual inspection, and only if the operator happens to check an instance that got the "wrong" number of runs.

**The actual fix used:** Rather than trying to track run-count, the resolution checked *current state directly* against an independent invariant — in this case, which of the two icon slots had a visible inner icon vs. a hidden spacer (a structural asymmetry that exists regardless of how many times the swap ran) — and used that to determine the correct target state directly, rather than trusting "has this been swapped once" bookkeeping.

**Proposed skill addition:** A new gotcha in `references/figma.md` (likely near the `COMPONENT_SET` / batch-mutation sections) stating: for any fix that is its own inverse (a swap, a mirror), prefer deriving the correct target state from an independent structural signal over re-running the operation — because "did this already run" is not reliably answerable from the operation's own side effects, and re-running an already-applied inverse-of-itself fix silently undoes it with no error.

## 2. Reordering a row whose sibling data lives elsewhere risks data-label misalignment

**What happened:** A bar chart's x-axis weekday-label row (`row`, 7 children) was flagged for the standard "does this need reversing" judgment call — but investigation found the actual bar rectangles are *not* children of the same row, or even close in the tree; the label row is one of several sibling `row` elements under a `graph` container, with the bars presumably rendered via some other mechanism not yet located. Reversing the label row alone, without confirming exactly how bars-to-labels correspondence is established, risks silently misaligning each label from the bar it's supposed to describe — a data-integrity bug, not just a cosmetic one.

**Why it's a distinct category from the earlier "hidden children" and "short label" heuristic gaps:** those were about *guessing the wrong element* within a row. This is about a row whose correctness depends on state *outside* the row entirely. No amount of inspecting the row's own children resolves it — the bars have to be found and their correspondence to labels confirmed first.

**Proposed skill addition:** A new subsection under Phase 2 (or wherever WRAP/reversal guidance lives) naming this as its own flag category: "a row whose visual correctness depends on a sibling or cousin element outside the row" — e.g. chart axis labels vs. chart bars, a legend vs. the thing it's a legend for. Flag for manual review by default; do not apply a reversal (full, per-row, or otherwise) until the actual data-to-label binding mechanism is located and confirmed compatible with reordering.

## 3. Chronological/calendar UI is a "stays LTR" category, extending Core Principle 5

**What happened:** A date-range navigator (prev/next week arrows flanking "5 לפברואר - 12 לפברואר") was found completely unchanged between the Hebrew original and the current (post-mechanical-phase) state — same arrow shapes, same positions. Rather than being an unresolved bug, this turned out to be correct: date/calendar navigation conventionally stays chronologically LTR (earlier-date-arrow on the left, later-date-arrow on the right) *regardless of the surrounding UI's reading direction*, the same way numerals and phone numbers stay LTR per Core Principle 5. This was inferred from the arrows being genuinely different assets (not a single rotated icon) sitting in the same configuration in both languages — a plausible, though not airtight, signal of an intentional convention rather than an unconverted bug.

**Why this is worth stating as a principle, not just a one-off observation:** without naming it, every future date-picker, calendar grid, or timeline component will independently re-trigger the "is this arrow supposed to look like this" uncertainty, and risk either (a) leaving a genuine bug unfixed because it superficially resembles this pattern, or (b) breaking a correct chronological-LTR component because it superficially resembles a directional-icon bug.

**Proposed skill addition:** Extend Core Principle 5 (`SKILL.md`) — currently scoped to "numerals, currency, phone numbers, dates, URLs, and code" — to explicitly include *chronological navigation controls* (calendar prev/next, timeline scrubbers, date-range pickers) as the same category: these encode a time axis, not a reading-direction axis, and should be evaluated against "does this represent chronological flow" rather than the standard element-order default. Note the verification caveat: "arrows are different assets, not one rotated" is corroborating evidence but not definitive proof of intentionality — the same evidence-standard discipline (prefer an independent reference when one exists) still applies before assuming a chronological UI element is correct as-is.
