# Which way in

This covers the moment after the project's direction is found and before any visual work starts: choosing one of three ways in, and saying which. It ends when the agent has named the way in and the Designer has either let it stand or corrected it. It runs on what is already loaded and the request, and it fixes no output.

1. **Name what is being changed and where it lives.** The way in follows from that. It is a Figma file or frame, a component that is already part of the design system, or the running product's code.
2. **Choose a sprint when the work is iterating a design in Figma.** Use it when the Designer wants to see the whole picture, compare options side by side, point at what needs attention and make their own tweaks. A sprint is the default for a design that is not yet approved.
3. **Choose formalizing only after the Designer has decided to formalize.** Use it for a component the Designer says should become part of the design system, or when the Figma file has gone stale beside the code. If they have not decided, it is a sprint, or a proposal to formalize that waits for their yes.
4. **Choose tuning in place when the change is to be seen live in the running product.** Use it when the visuals are tuned in the code, and when the project was never decomposed into Figma.
5. **Ask once when a request fits two, naming both in plain words.** A sprint can end in a decision to formalize, so do not start with both. One question, and then go.
6. **Say the chosen way in before starting, in one line.** The Designer can then redirect in a word.

If the request names neither a Figma area nor the running product, and nothing in the project shows either, ask where the work lives. Do not guess a way in and begin.

*Do:* "This is a sprint: you want to look at options for the schedule screen in Figma before anything changes in the product."
*Don't:* start laying frames out and mention afterward that this was a sprint.
